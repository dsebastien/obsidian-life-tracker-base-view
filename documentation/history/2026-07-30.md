# 2026-07-30

## Custom filename date patterns (issue #139)

Filename date parsing is now user-configurable. Notes named anything other than
the five built-in ISO formats (`YYYY-MM-DD`, `YYYY-Www`, `YYYY-MM`, `YYYY-Qq`,
`YYYY`) previously resolved no date anchor.

- New `src/utils/filename-date.utils.ts`: `{{token}}` pattern compiler
  (`{{date}}`, `{{year}}`, `{{month}}`, `{{day}}`, `{{week}}`, `{{quarter}}`,
  plus `*` wildcards), validator, example renderer, the built-in patterns, the
  configured-pattern registry, `parseDateFromFilename` and `getDateFromISOWeek`.
  Everything filename-related moved out of `date.utils.ts` so the dependency
  stays one-way; the moved tests moved with it.
- `filenameDatePatterns` setting (`{ id, pattern }[]`, default `[]`), compiled
  into the registry by `plugin.applyDateSettings()` on load and on every
  settings update (`applyWeekStart` renamed to cover both concerns).
- New "Dates" settings tab (`date-settings-section.ts`) with the pattern list
  editor: per-pattern validation error or live matching example, plus a token
  reference. "First day of the week" moved there from "Visualizations".
- "Capture today" benefits automatically (it filters on daily granularity).

## Decisions

- Token vocabulary copied from `obsidian-starter-kit-plugin`'s
  `expression-evaluator.ts` so the syntax is the same across the plugin family.
  `obsidian-ai-editor` has no equivalent mechanism.
- Granularity is inferred from the token set rather than configured — one less
  thing to get wrong, and it cannot contradict the pattern.
- Custom patterns are tried before the built-ins, which always remain as a
  fallback: no migration, no breakage for existing vaults.
- `*` chosen as the wildcard because it cannot appear in a filename, so it is
  unambiguous. Everything else in a pattern is regex-escaped.
- Month names (`January`) deliberately not supported: locale handling would be
  half-broken for non-English vaults. Numeric tokens only.

## Open questions

- Should patterns be matched against the full path (folder + name) as well as
  the basename? Currently basename only, like the built-ins.
- Needs manual runtime verification in a vault (settings UI states, a matching
  note landing on the right heatmap cell, "Capture today").

## Vault audit (dsebastien's vault)

Checked `~/notesSeb` for #139: **no custom patterns needed**. Every periodic
note already uses a built-in format (2083 files: daily `2026-07-23`, weekly
`2026-W30`, monthly `2026-07`, quarterly `2026-Q3`, yearly `2026`); zero
deviations. Daily notes live under `40 Journal/41 Daily Notes/{{year}}/{{week}}`
but only the basename is parsed, so the folder shape is irrelevant.

One real config smell found: `Health (Base).base`'s Life Tracker view sets
`dateAnchorProperty: note.created`, but the daily notes carry `date`, not
`created` — the anchor silently falls through to the filename (which works).
Recommend pointing it at `note.date` or clearing it.

## Decisions (batch)

- **Chart.js decimation deliberately not enabled** (#104 suggested it): the
  plugin requires a `linear`/`time` x scale with `parsing: false`, and these
  charts use a category scale of formatted period labels — it would silently do
  nothing. Marker suppression gives the actual win without dropping data points,
  which matters for tracked data where a single day is meaningful. Migrating the
  cartesian x axis to a time scale is a possible follow-up.
- The **star is always the same outline icon**; CSS fills it gold when pinned.
  Same shape in both states, so the action row's layout is identical on every
  card (visual stability rule).
- **`common-value` buttons** from #125 were left out: bounded properties already
  get one-tap entry from the slider, and the issue's stated use cases (water,
  pushups) are unbounded counters.

## Adversarial review (codex, gpt-5.6-sol high) — findings fixed

Two rounds (review, then verify-the-fixes). Round 1: ten findings, all real:

- **NUL byte in source**: the tag-cloud signature separator was a literal `\0`
  (and then a literal `\x1f`), which made git treat the `.ts` file as binary.
  Now an escaped `'\u001f'` constant; added a repo-wide control-character check.
- **Tag-cloud signature ignored `maxFrequency`**: font sizes are relative to the
  overall max, so a frequency change outside the rendered slice left visible
  tags at the wrong size. Included in the signature.
- **`handleResize` measured after the resize**: see #104 above.
- **Skeleton count assumed one card per item**: see #135 above.
- **Roving tabindex reset on in-place heatmap updates**: the Tab stop is now
  preserved where the user left it.
- **Stale pins written back**: `toggleCardPin` now reconciles against the
  current effective order before persisting.
- **Default-value wrapper clipped the stepper** (`max-width: 180px` +
  `overflow: hidden`, and `w-full` on the mobile input): the wrapper gets a
  marker class that lifts the cap, step buttons are `flex-shrink-0`, and the
  input flexes inside a stepper on mobile.
- **Docs overstated pinning**: pins are per property (a property's cards render
  together) and the context-menu entry exists for property cards only —
  corrected in `docs/usage.md` and the business rules.
- **`format:check` failed** on two docs edited after the last format run.

Round 2 (verifying those fixes) found five more, also fixed:

- **Heatmap empty-data early return kept the old grid's references**, so a later
  in-place update patched a detached grid and the card stayed stuck on the empty
  state. Extracted `releaseRenderedGrid()` and call it on both render paths and
  in `destroy()`.
- **The single-card rebuild path never wired the pin control**, so any config
  change (colour, scale, aggregation…) made the star vanish until the next full
  render. Now wired like the full path.
- **The `max-width: 180px` cap still won on specificity** over the stepper
  marker class, and the mobile `order: 2` applied to steppers nested in the
  "Use default" row, putting the button before the −/input/+ group. Both
  selectors tightened.
- **README still said "right-click any card" to pin** — overlay right-click
  opens the overlay editor. Reworded.
- **A stray control character and a Prettier violation** in this history file.

Round 3 (verifying round 2) found five more, also fixed:

- **Heatmap live→empty could take the in-place path**: empty data reports today
  as its min/max, which can satisfy `canUpdateInPlace()`, leaving a grid of blank
  cells instead of the empty state. `update()` now re-renders whenever the new
  data has no cells.
- **Mobile stepper rendered −, +, input**: the generic mobile rule gives
  `.lt-editor-input--number` `order: 2`, which also applied inside the stepper.
  Reset to `order: 0` there.
- **Popout windows**: `target instanceof Element` is false for nodes from
  another window realm, which would have made heatmap delegation inert and every
  control swipeable in a popout. Added `getEventElement()` (duck-types `closest`)
  and used it in both places.
- **Tooltip leak**: tag cloud and timeline built a new body-level tooltip on
  every structural render without destroying the previous one.
- **Pinning docs still overstated**: unconfigured cards and empty-state cards
  have no star (no header is rendered); documented precisely.

## Live-testing fixes (pinning)

First hands-on test found the star doing nothing. Cause: `toggleCardPin` (and
`resetCardOrder`, same latent bug) cleared `previousOrderSignature` to "force" a
full render — but `canDoIncrementalUpdate()` reads a null signature as "nothing
to compare" and _allows_ the incremental path, so the DOM order never changed
and the card was never re-rendered (so the star's state never updated either).
Both now set `forceFullRender`, the flag `rebuildView()` actually consumes.

The star also flips optimistically on click, so the control answers immediately
instead of waiting for the debounced rebuild.

Icon: always the outline `star`; `.lt-pin-btn--pinned` fills it with
`var(--color-yellow)`. The crossed-out `star-off` is gone, and the context menu
uses the same star.

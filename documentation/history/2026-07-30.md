# 2026-07-30

## Custom filename date patterns (issue #139)

Filename date parsing is now user-configurable. Notes named anything other than
the five built-in ISO formats (`YYYY-MM-DD`, `YYYY-Www`, `YYYY-MM`, `YYYY-Qq`,
`YYYY`) previously resolved no date anchor.

- New `src/utils/filename-date.utils.ts`: `{{token}}` pattern compiler
  (`{{date}}`, `{{year}}`, `{{month}}`, `{{day}}`, `{{week}}`, `{{quarter}}`,
  plus `*` wildcards), validator, example renderer, the built-in patterns, the
  configured-pattern registry, `parseDateFromFilename` and `getDateFromISOWeek`.
  Everything filename-related moved out of `date.utils.ts` so the dependency
  stays one-way; the moved tests moved with it.
- `filenameDatePatterns` setting (`{ id, pattern }[]`, default `[]`), compiled
  into the registry by `plugin.applyDateSettings()` on load and on every
  settings update (`applyWeekStart` renamed to cover both concerns).
- New "Dates" settings tab (`date-settings-section.ts`) with the pattern list
  editor: per-pattern validation error or live matching example, plus a token
  reference. "First day of the week" moved there from "Visualizations".
- "Capture today" benefits automatically (it filters on daily granularity).

## Decisions

- Token vocabulary copied from `obsidian-starter-kit-plugin`'s
  `expression-evaluator.ts` so the syntax is the same across the plugin family.
  `obsidian-ai-editor` has no equivalent mechanism.
- Granularity is inferred from the token set rather than configured — one less
  thing to get wrong, and it cannot contradict the pattern.
- Custom patterns are tried before the built-ins, which always remain as a
  fallback: no migration, no breakage for existing vaults.
- `*` chosen as the wildcard because it cannot appear in a filename, so it is
  unambiguous. Everything else in a pattern is regex-escaped.
- Month names (`January`) deliberately not supported: locale handling would be
  half-broken for non-English vaults. Numeric tokens only.

## Open questions

- Should patterns be matched against the full path (folder + name) as well as
  the basename? Currently basename only, like the built-ins.
- Needs manual runtime verification in a vault (settings UI states, a matching
  note landing on the right heatmap cell, "Capture today").

## Decisions (batch)

- **Chart.js decimation deliberately not enabled** (#104 suggested it): the
  plugin requires a `linear`/`time` x scale with `parsing: false`, and these
  charts use a category scale of formatted period labels — it would silently do
  nothing. Marker suppression gives the actual win without dropping data points,
  which matters for tracked data where a single day is meaningful. Migrating the
  cartesian x axis to a time scale is a possible follow-up.
- The **star is always the same outline icon**; CSS fills it gold when pinned.
  Same shape in both states, so the action row's layout is identical on every
  card (visual stability rule).
- **`common-value` buttons** from #125 were left out: bounded properties already
  get one-tap entry from the slider, and the issue's stated use cases (water,
  pushups) are unbounded counters.

## Live-testing fixes (pinning)

First hands-on test found the star doing nothing. Cause: `toggleCardPin` (and
`resetCardOrder`, same latent bug) cleared `previousOrderSignature` to "force" a
full render — but `canDoIncrementalUpdate()` reads a null signature as "nothing
to compare" and _allows_ the incremental path, so the DOM order never changed
and the card was never re-rendered (so the star's state never updated either).
Both now set `forceFullRender`, the flag `rebuildView()` actually consumes.

The star also flips optimistically on click, so the control answers immediately
instead of waiting for the debounced rebuild.

Icon: always the outline `star`; `.lt-pin-btn--pinned` fills it with
`var(--color-yellow)`. The crossed-out `star-off` is gone, and the context menu
uses the same star.

## Custom heatmap color schemes (#82) + colorblind-friendly palettes (#136)

Heatmaps could only shade one hue by intensity, which makes mood-style 1..5
scales unreadable (2 vs 3 is a shade). They can now map specific values to
specific colors, and both heatmaps and charts gained CVD-safe palettes.

- `HeatmapColorScheme` is a discriminated union: `{ kind: 'gradient', empty,
levels[5] }` (unchanged behavior) or `{ kind: 'discrete', empty, mapping,
fallback? }`. Discrete mode ignores min/max entirely.
- `color.utils.ts` gained `resolveHeatmapCellColor` (the single entry point
  renderers use), `isDiscreteHeatmapScheme`, `normalizeHeatmapColorScheme`,
  `asChartColorScheme`, `createDefaultDiscreteScheme`, `nextDiscreteEntryColor`.
  `getHeatmapColor`/`applyHeatmapColorScheme` narrowed to gradient schemes.
- New `applyCellColor()` in the renderer, used by **all five** granularity paths
  _and_ the in-place update path — the plan in the issue only covered the daily
  one, and the other four would have silently kept ignoring discrete schemes.
- The legend follows the scheme: "Less → More" for gradients, one labelled
  swatch per entry for discrete (unreadable otherwise).
- Storage: `colorScheme` widened to `StoredColorScheme = ChartColorScheme |
HeatmapPresetName | HeatmapColorScheme`. Charts narrow it with
  `asChartColorScheme()`, so a heatmap's inline object or a heatmap-only preset
  name resolves to the default chart palette instead of leaking into a
  `ChartConfig`.
- UI: heatmaps get their own "Colors" dropdown in the card popover (gradients +
  "Custom mapping…" + "Default"), with a mapping editor modal (value input,
  color picker, remove, add entry, fallback color). The settings preset dropdown
  is now type-aware too.
- #136: `colorblind` chart scheme (Okabe-Ito 8 colors), `viridis` and `cividis`
  heatmap gradients, and new mappings seed from a CVD-safe blue → orange ramp
  with added entries cycling Okabe-Ito.

## Decisions (#82/#136)

- **No settings migration.** The issue's plan called for normalizing legacy
  `{ empty, levels }` objects on load, but no such object has ever been
  persisted — presets are code constants and view config stores names. Instead
  `normalizeHeatmapColorScheme()` validates at point of use (view config comes
  from a `.base` file, so it can be anything) and upgrades the bare shape for
  free.
- **Heatmaps and charts no longer share one options list.** They were coupled by
  coincidence (green/blue/purple/orange/red exist in both); adding viridis and
  the Okabe-Ito scheme made the overlap accidental rather than meaningful.
- **Inline background only for discrete cells.** Gradient rendering keeps its
  CSS variables and level classes — no churn, and no `!important` needed since
  inline styles already win. The in-place update path must _clear_ the inline
  background when the scheme is not discrete, or a gradient switch would keep
  the old color.
- **Accessible by default, not by opt-in** (#136): a fresh custom mapping is
  already colorblind-safe, and deliberately avoids red → green — the axis most
  deficiencies collapse — as its default ramp.
- **Modal closes the popover first**, like the scale modal (the reference-line
  modal stacks instead, which means two focus traps and two Escape handlers).

## Open questions (#82/#136)

- Range mappings (`1-2 → red`) deferred until asked for; exact values cover the
  issue as filed.
- Presets (settings tab) store scheme _names_ only — a custom mapping is
  per-card. Worth revisiting if users ask for "all mood properties use this
  mapping".
- **Needs manual runtime verification in a vault**: the mapping editor (add /
  remove / fallback / cancel-discards), discrete cells actually painting per the
  mapping, the discrete legend staying pinned at the card bottom without
  breaking visual stability across cards, switching a card discrete → gradient →
  discrete, and the new viridis/cividis/colorblind entries in all three
  dropdowns (view options, card popover, settings presets).

## Value polarity (#21) + value/range emojis (#22)

Shipped together: #21 is what makes #22's defaults meaningful, and #21 names #22
as its payoff ("that way, we can map emojis or other fun things").

- `polarity` on `PropertyDefinition`: `neutral` (default) | `higher-is-better` |
  `lower-is-better`. Optional field, absent reads as neutral — definitions from
  older versions and from the Starter Kit plugin keep working untouched.
- **Trend arrow** is the behavior the business rules explicitly deferred to #21
  ("the arrow color stays neutral… see issue #21"). It now colors green/red by
  sentiment and words it as improving/worsening. A flat trend and a neutral
  property both stay muted.
- **Default heatmap gradient** by polarity (green / red), as the _lowest_
  precedence step: per-card scheme → view-wide setting → polarity → green.
- `valueEmojis` on `PropertyDefinition`: value or range → emoji. New
  `emoji-mapping.utils.ts` parses keys (`3`, `1-2`, `1..2`, `-5--1`, reversed
  ranges normalized) and resolves values, exact keys beating ranges.
- Emojis render in heatmap and chart tooltips, and as one-tap buttons under the
  number editor — the "editing through emojis" half of the issue. Not in compact
  grid cells (visual stability).
- New settings editors: a "Value direction" dropdown and a value-emoji list,
  offered only for properties whose values are numeric (number, checkbox, or
  text with a value mapping).

## Decisions (#21/#22)

- **Neutral is the default and means silence.** The plugin must not guess
  whether a rising number is good news; every polarity-driven behavior is opt-in.
- **Color is never the only channel.** The arrow glyph and the wording carry the
  same meaning as the green/red — consistent with the #136 work earlier today.
- **Chart palettes are not polarity-driven.** A series color identifies the
  series, not its goodness; only the trend indicator carries sentiment.
- **Overlay charts stay neutral** — several properties, no single polarity — so
  `getVisualizationConfig` simply gets no definition for them.
- **Ranges are in scope for #22** (they were deferred in #82) because the issue
  asks for "values or ranges" by name.
- **`valueEmojis` is a separate field from `valueMapping`**, not an extension of
  it: they run in opposite directions (text → number for input vs number → emoji
  for display) and a property can legitimately use both.
- CSS: the trend sentiment class lands on the trend row's first child, which
  `.lt-chart-trend-item:first-child` (0,2,0) would otherwise win over — resolved
  with the documented doubled-class idiom rather than `!important`.

## Open questions (#21/#22)

- **Polarity-derived heatmap color may be inert**: it only applies when
  `getStringConfig(getConfig, 'heatmapColorScheme')` returns undefined. If
  Obsidian materializes a declared view-option `default` into stored config, that
  read returns `'green'` even when untouched and polarity never gets a turn. The
  trend arrow is unaffected (it does not read view config). **Verify in a vault.**
- Emoji quick-entry is wired into the number editor only. Checkbox properties
  can have a polarity but get no emoji buttons yet.
- **Needs manual runtime verification**: the trend arrow coloring and wording for
  both polarities, the emoji row in the capture modal (selection state, range
  buttons recording the lower bound, 44px tap targets on mobile), the settings
  editors (invalid-key marker, add/remove, the blur-then-rerender dance the
  existing value-mapping editor uses), and emoji prefixes in both tooltip kinds.

## Adversarial review (codex, gpt-5.6-sol high) — #21/#22

Two rounds. Round 1: eight findings, all verified real before fixing.

- **Config-only definition changes were swallowed** (regression this work
  introduced). `property-definitions-changed` cleared the cache and called
  `onDataUpdated()`, which takes the _incremental_ path when the data signature
  is unchanged — fine while definitions only carried `valueMapping` (which
  changes the data), but polarity and emojis are config, so nothing updated
  until reload. Now sets `forceFullRender`, like the preset path already did.
- **Emoji key editing orphaned entries**: the row's handlers used the
  render-time key, so typing `10` into a blank row wrote `1` _and_ `10`, and the
  emoji field then wrote to a key that no longer existed. Rows now track their
  current key/emoji. The existing `valueMapping` editor has the same latent bug
  — left alone, but worth a follow-up issue.
- **Renaming onto an existing key silently destroyed it** — now rejected and
  marked invalid.
- **Copying a property definition dropped both new fields** (the copy is built
  field by field).
- **Range buttons highlighted only at their lower bound**, and overlapping
  ranges could light up two buttons. Extracted `findEmojiEntry` as the single
  precedence source, shared by tooltips and the editor's selection state.
- **Bubble tooltips had no emoji** while the docs claimed all chart points —
  added, and the docs now name the covered chart types.
- **`.lt-input-invalid` (0,1,0) lost** to Obsidian's `input[type='text']`
  rules (0,1,1) — doubled-class idiom, as the CSS rules require.
- **Exact keys overflowing to `Infinity`** were accepted and could never match.

Round 2 (verifying those fixes) found three more:

- **The duplicate check read the render-time snapshot**, so sibling rows renamed
  since the last render were invisible: `1→3` then `2→3` still collided, and
  `1→3→1` reported a phantom duplicate. Now reads live settings.
- **`forceFullRender` in the `full` catch-all was over-broad** — that branch
  serves every untyped `updateSettings` call, and forcing a rebuild there is a
  heavy default. Reverted; instead the polarity and emoji editors now announce
  `{ type: 'property-definitions-changed' }`, which is the branch that forces it.
  (The reviewer also claimed confetti/animation changes route through `full` —
  they do not, they have their own branches.)
- **Per-keystroke `updateSettings` calls can persist out of order** — two rapid
  edits both start `saveData`, and the later write can land first. **Not fixed
  here**: it is pre-existing and plugin-wide (every settings text field has this
  shape, including the `valueMapping` editor this one was modelled on), and
  fixing it properly means serializing writes in `saveSettings`, which is a core
  change well outside these two issues. Worth its own issue.

## Follow-ups from the #21/#22 review — now fixed

The three items deferred out of that review have been closed.

- **Settings writes are serialized.** New `src/utils/serial-queue.utils.ts`
  (`createSerialQueue`), used by `plugin.saveSettings()`. Editors call
  `updateSettings` per keystroke, so two `saveData` calls could be in flight at
  once and land out of order, persisting the _older_ snapshot — visible only
  after a restart. Each queued write persists the settings as they are when it
  runs, so the last write always wins; a failed write rejects for its own caller
  without wedging the queue. Extracted as a utility rather than inlined so it is
  actually testable (the plugin class needs the Obsidian runtime).
- **The `valueMapping` editor had the same orphaned-key bug** as the emoji
  editor: typing `ok` into a fresh row left an orphaned `o` entry, and the number
  field then wrote to a key that no longer existed. Same fix — track the current
  key, reject renames onto an existing key, read live settings for the duplicate
  check. It now also announces `property-definitions-changed`.
- **The polarity-derived heatmap default is no longer a coin flip.** It used to
  depend on `getStringConfig('heatmapColorScheme')` returning undefined, which
  fails if Obsidian materializes a declared view-option `default` into stored
  config. The view option now defaults to an explicit `auto` sentinel
  (`HEATMAP_SCHEME_AUTO`, labelled "Automatic (by value direction)"), which the
  resolver reads as "nothing chosen". Deterministic either way, and it gives
  users a visible control instead of hidden behavior.

### Decisions

- **`auto` as a sentinel beats guessing.** Trying to infer "did the user touch
  this?" from a value that equals the default is unknowable by construction;
  adding a value that _means_ untouched removes the question. Existing views that
  stored `green` keep green — that reads as a deliberate choice, which it was.
- **The serial queue is a utility, not a method.** `saveSettings` lives on a
  class extending Obsidian's `Plugin`, which cannot be instantiated under
  `bun test`; the queue's ordering guarantees are exactly what needs proving.
- Per-keystroke edits are safe for render cost: `onDataUpdated` is debounced, so
  the forced full render collapses to one rebuild.

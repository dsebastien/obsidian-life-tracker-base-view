# 2026-08-11

## Reset button overflowed the visualization settings dialog (#143)

`.lt-card-popover-header` was a single non-wrapping flex row. The number of
buttons varies with the visualization type (image export only for Chart.js
types, Remove only when removable), so at seven buttons the row ran past the
popover's 692px max-width and Reset hung outside it.

- Header wraps now (`flex-wrap`), buttons keep their intrinsic width
  (`shrink-0`) instead of being squeezed.
- Dropped `justify-between`: with wrapping it would spread the last row's
  buttons across the full width.
- The mobile override no longer repeats `flex-wrap`/`gap-2`.

## Column buttons had no icons, charts did not fill the card (#144)

Two unrelated causes behind one issue.

**Missing icons.** All plugin rules live in `@layer lt-components`. Obsidian's
`app.css` is unlayered, and unlayered author styles beat _any_ layered rule
regardless of specificity — so `button { padding: var(--size-4-1)
var(--size-4-3); height: var(--input-height) }` won over the layered `p-0`/`h-5`
of `.lt-control-btn`. On the fixed-width 20px +/- buttons, 12px of side padding
left a zero-width content box and the icon was squeezed to nothing. The Overlay
and Reset-order buttons escaped it because they are `w-auto`.

- Moved `.lt-control-btn` and its variants out of the layer, into the existing
  "intentionally unlayered" region at the end of `styles.src.css`. The
  declarations themselves are unchanged.
- Icon size uses a doubled class (0,2,1) so it also outranks Obsidian's
  `svg.svg-icon { width: var(--icon-size) }` (0,1,1), and any theme's copy of it
  — themes load after plugin CSS.

**Chart did not use the card width.** With `maintainAspectRatio: true` and
`aspectRatio: 2`, Chart.js derived the height from the width, found it taller
than the card, then shrank the _width_ back to `height * aspectRatio` (see
`getMaximumSize` in Chart.js' DOM helpers). Result: a small chart pinned left
with the rest of the card empty, worse with every added column.

- `maintainAspectRatio: false` in all five initializers; dropped the now-inert
  `aspectRatio`.
- `.lt-chart` is `relative` with `min-height: 200px` (was 150px), meeting
  Chart.js' requirement of a dedicated, relatively positioned container with a
  definite height.
- `.lt-chart-canvas` is absolutely positioned. In flow, a `width: 100%` canvas
  keeps the 2:1 ratio of its width/height attributes, and in an auto-height card
  that ratio drove the card's height instead of the reverse — charts grew to
  ~700px tall. Out of flow, the container is measurable without the canvas.

### Verification

No live vault, so both fixes were checked by extracting `app.css` from the
installed Obsidian's `obsidian.asar`, loading it in Chrome ahead of the built
`styles.css`, and rebuilding the control bar, card and popover DOM. Measured:
+/- buttons 20x20 with 10x10 icons (previously 0 wide), zero header buttons
past the popover edge, canvas at the full container width.

**Still needs manual runtime verification** in a real vault: card heights at
2-6 columns, maximized cards, the heatmap/timeline/tag-cloud types that share
`.lt-card`, and mobile.

## Running totals for numeric properties (#142)

New per-visualization **Running total** option on line and area charts: plots
the cumulative total instead of the per-period value, so `pages_read` of 20, 15,
30 reads as 20 → 35 → 65. Plan and rationale in
`documentation/plans/142-running-totals.md`.

Decisions taken with the user before building:

- A separate `runningTotal?: boolean`, **not** a third `AggregationMethod` value
  as the issue proposed. Within-period combining and across-period accumulation
  are different questions, and conflating them would have made "average per
  week, cumulative" unexpressible.
- Replaces the plotted series rather than adding an overlay dataset.
- Accumulation starts at 0 at the left edge of the visible time frame; no data is
  read from outside the window.
- Line and area only.
- Presets and overlays are out of scope, mirroring `movingAveragePeriod` (#101),
  which is also per-visualization config only.

Implementation notes:

- `computeRunningTotal()` in `chart-aggregation.utils.ts` is pure and covered by
  specs. Nulls are neither gaps nor zeros: a period with no value carries the
  previous total forward, while periods before the first value stay null.
- Applied in the numeric branch of both `render()` and `updateCartesianChart()`,
  before `applyMovingAverage()`, so a moving average smooths the series that is
  actually plotted. The list-data branch is untouched.
- The dataset label gains a ` (running total)` suffix — it feeds both the legend
  and the CSV export, and the series no longer means what the bare property name
  says.
- The trend row still works on the plotted series. On a cumulative series it
  trends up by construction; `showTrendInfo` already turns it off. Left as is
  rather than special-cased.

**Still needs manual runtime verification**: the dropdown on line and area
cards, with `sum` and with `average`, with a gap mid-range, alongside a moving
average, and that the choice survives a reload.
